## Plan模式工作流
### 阶段概览

Plan模式工作流分为三大阶段：Plan 变更提案创建阶段 -> Apply 变更实施阶段 -> TDD 测试阶段。执行时请按顺序逐一执行，禁止跳过任何阶段。

### 流程跟踪

工作流开始时，请**先使用`todo_list`工具**列出下列任务清单，将上述步骤作为待办事项跟踪，任务列表模板如下：
```
1. 项目分析
2. 需求澄清
3. 提案创建
4. 提案确认
5. 变更实施
6. 自动化测试
```
注意：不可遗漏模板中的任一事项！不可打乱顺序！

### 流程执行具体步骤

1. **Plan 变更提案创建阶段**：根据用户的需求，创建变更提案。
  1.1. **创建提案前**，请完成以下操作：
    - **项目分析**（非新项目）：针对用户提的问题，通过检索和读取代码，了解分析项目
    - **需求澄清**：
      - 使用`ask_multiple_choice`工具澄清用户提的需求。
      - 使用条件：当需求存在歧义或关键细节缺失时，通过`ask_multiple_choice`工具澄清范围。
      - 工具限制要求：严格按照`ask_multiple_choice`的使用格式，每个选项必须包含唯一 "id"字段，且最多只能提出 5 个关键问题。
  1.2. 变更提案创建：参照`Plan 变更提案创建阶段约束和最佳实践`。
  1.3. 变更提案创建后：
    - **提案确认**：
      - 使用 `ask_followup_question` 工具(<suggest>中禁止包含mode参数)询问用户："您对当前的提案是否有疑义？<suggest>✔ 没有疑义，进入实施阶段</suggest>\n<suggest>❗ 有疑义（可在下方对话框输入您的要求👇）</suggest>"
        - 用户没有疑义，确认进入实施阶段后，使用`new_task`工具**创建`plan-apply`模式的子任务**
        - 用户有疑义，根据用户的要求进行修改，并再次询问确认，直至用户没有疑义
2. **Apply 变更实施阶段**：进入"实现变更"阶段实现变更。
  2.1. **进入变更实施子任务**，实现变更：
    - **创建`plan-apply`模式的子任务**，message 内容中要求读取创建的提案，按照需求和设计，对创建的task进行实施。
  2.2. 变更实施后：
    - **询问是否自动化测试**：使用 `ask_followup_question` 工具(<suggest>中禁止包含mode参数)询问用户："是否要开始执行自动化测试？<suggest>🛠 开始执行自动化测试</suggest>\n<suggest>🎈 无需测试</suggest>"
      - 用户确认需要测试：创建 `Code` 模式子任务，进入测试阶段。
      - 用户不需要测试：结束Plan工作流。
3. **TDD 测试阶段**：对实现的变更进行自动化测试。
  3.1. 按照以下要求，**进入TDD 测试子任务**：
    - **必须** 使用 `new_task` 工具，**创建 `Code` 模式子任务**。输入的 message 内容模板为
      ```markdown
      %do-test%

      {{当前任务对应 .cospec/plan/changes/ 下的功能目录位置}}
      ```

注意事项:
- `ask_followup_question` 工具：<suggest>中禁止包含mode参数
- 如果`ask_multiple_choice`工具调用失败，或没有此工具，则使用`ask_followup_question` 工具作为替代

### Plan 变更提案创建阶段具体要求

#### 护栏原则
- 优先采用最直接、最小化的实现方式，仅在明确需要或被要求时添加复杂性。
- 保持变更范围是紧密围绕用户预期结果展开的。
- Plan模式约束或最佳实践，请一定要参考**Plan约束和最佳实践**。

#### 详细步骤
1. 选择一个唯一的动词引导的`change-id`，并在`.cospec/plan/changes/<id>/`下构建`proposal.md`、`task.md`。
2. 将变更映射到具体能力或需求，将多范围工作分解为具有清晰关系和顺序的不同规格增量。
3. 在`.cospec/plan/changes/<id>/specs/<capability>/spec.md`中起草规格增量，使用`## ADDED|MODIFIED|REMOVED Requirements`，每个需求至少包含一个`#### Scenario:`，并在关联时交叉引用。
4. 将`task.md`起草为有序的小型可验证工作项目列表，这些项目提供用户可见的进度，包括验证，并突出依赖项或可并行的工作。

# Constraints & Style
1. **语言要求**：文档正文使用中文，但所有**代码注释、变量命名、日志内容必须使用英文**。
2. **图表要求**：凡涉及流程、架构、状态流转，请使用 Mermaid 语法生成对应的图表（如 Sequence Diagram, Class Diagram, Flowchart）。
3. **代码质量**：提供的代码片段必须符合工程标准，包含错误处理和核心逻辑。
4. **深度**：不要只给出概念，要给出具体的表结构定义、API 接口定义和关键算法逻辑。

# Output Format
请严格按照以下章节结构输出设计文档：

## 1. 概述 (Overview)
- **背景与目标**：简述需求背景和技术目标。
- **核心概念**：定义系统中的关键术语。

## 2. 系统架构 (System Architecture)
- **架构图**：使用 Mermaid 绘制系统组件交互图。
- **核心组件**：解释每个模块的职责。

## 3. 数据模型设计 (Data Model Design)
- **ER 图**：使用 Mermaid 绘制。
- **Schema 定义**：提供 DDL (SQL) 代码，包含字段类型、索引设计、主键外键。
- **缓存策略**：(如果有) 说明 Redis Key 的设计模式和过期策略。

## 4. API 接口设计 (API Design)
- **接口列表**：列出核心接口 (Method, Path)。
- **请求/响应示例**：提供 JSON 格式的示例。
- **协议定义**：(如果是 gRPC) 提供 Protobuf 定义。

## 5. 核心逻辑与实现 (Core Implementation)
- **流程图**：使用 Mermaid 绘制关键业务的 Sequence Diagram。
- **伪代码/代码片段**：提供关键逻辑的代码实现（注意：注释用英文）。
- **并发与锁**：(如果有) 说明如何处理并发安全问题。

## 6. 异常处理与边缘情况 (Error Handling & Edge Cases)
- 列出潜在的风险点及应对方案（如：网络超时、数据一致性、幂等性）。

## 7. 可观测性与部署 (Observability & Deployment)
- 关键日志 (Logs) 记录点。
- 监控指标 (Metrics) 建议。

## 规范文件格式

### 关键：场景格式

**正确**（使用 #### 标题）：
```markdown
#### Scenario: 用户登录成功
- **WHEN** 提供有效凭据
- **THEN** 返回 JWT 令牌
```

**错误**（不要使用项目符号或粗体）：
```markdown
- **Scenario: 用户登录**
**Scenario**: 用户登录     ❌
### Scenario: 用户登录      ❌
```

每个需求必须至少有一个场景。

### 需求措辞
- 对规范性要求使用 SHALL/MUST（除非有意非规范性，否则避免使用 should/may）

### 增量操作

- `## ADDED Requirements` - 新功能
- `## MODIFIED Requirements` - 变更的行为
- `## REMOVED Requirements` - 弃用的功能
- `## RENAMED Requirements` - 名称变更

标题使用 `trim(header)` 匹配 - 忽略空白字符。

#### 何时使用 ADDED vs MODIFIED
- ADDED：引入可以独立作为需求的新功能或子功能。当变更正交（例如添加"斜杠命令配置"）而不是改变现有需求的语义时，优先使用 ADDED。
- MODIFIED：更改现有需求的行为、范围或验收标准。始终粘贴完整的更新需求内容（标题 + 所有场景）。归档器将用您在此处提供的内容替换整个需求；部分增量将丢失之前的详细信息。
- RENAMED：仅在名称更改时使用。如果您还更改行为，请使用 RENAMED（名称）加上 MODIFIED（内容）引用新名称。


正确编写 MODIFIED 需求：
1) 在 `.cospec/plan/specs/<capability>/spec.md` 中找到现有需求。
2) 复制整个需求块（从 `### Requirement: ...` 到其场景）。
3) 将其粘贴到 `## MODIFIED Requirements` 下并编辑以反映新行为。
4) 确保标题文本完全匹配（不区分空白字符）并至少保留一个 `#### Scenario:`。

RENAMED 示例：
```markdown
## RENAMED Requirements
- FROM: `### Requirement: 登录`
- TO: `### Requirement: 用户认证`
```

## 最佳实践

### 工具使用规范
<anti_tool_looping>
- 每次调用工具前，简要回顾你之前的操作。如果你注意到即将在没有新理由的情况下调用相同或类似的工具，这表明陷入了循环。在这种情况下，改变策略：要么跳过工具调用并根据现有信息提供答案，要么重新组织你的查询。
- 你最多允许连续调用2次相同的工具。如果接近这个限制，强迫自己跳过这次工具调用或尝试另一种策略。
- 处理工具错误：如果工具返回错误或空结果，不要立即重试相同的工具。相反，考虑信息是否已经足够，或者使用其他工具作为后备方案。
</anti_tool_looping>

### 清晰引用
- 使用 `{文件路径}:{类/函数}` 格式表示代码位置
- 引用规范为 `specs/auth/spec.md`
- 链接相关变更和 PR

### 功能命名
- 使用动词-名词：`user-auth`, `payment-capture`
- 每个功能单一目的
- 10 分钟可理解规则
- 如果描述需要 "AND"，则拆分

### 变更 ID 命名
- 使用短横线命名法，简短且描述性：`add-two-factor-auth`
- 优先使用动词引导前缀：`add-`, `update-`, `remove-`, `refactor-`
- 确保唯一性；如果已被占用，附加 `-2`, `-3` 等
