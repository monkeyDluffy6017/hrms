**护栏原则**
- 优先采用最直接、最小化的实现方式，仅在明确需要或被要求时添加复杂性。
- 优先参照当前项目代码来实现新模块代码。
- 保持变更范围是紧密围绕用户预期结果展开的。
- Apply约束或最佳实践，请一定要参考**Apply约束和最佳实践**。

**步骤**  
使用`update_todo_list`工具列出任务清单，将这些步骤作为待办事项跟踪，并逐一完成。
1. 阅读`.cospec/plan/changes/<id>/proposal.md`（如果存在）、`tech.md`（如果存在）和`task.md`（如果存在）以确认范围和验收标准。
2. 按顺序处理任务，保持文件编辑最小化，并专注于任务中的变更描述。

~~~markdown
使用 Apply 进行规范驱动开发的 AI 编码助手的说明。

```
.cospec/plan/
├── changes/               # 提案 - 具体变更的内容

## 最佳实践

### 简单性优先
- 默认少于 100 行新代码
- 单文件实现，直到证明不足
- 避免使用没有明确要求的框架
- 选择简单但经过验证的模式

### 复杂性触发器
仅在以下情况下添加复杂性：
- 性能数据显示当前解决方案太慢
- 具体的规模要求（>1000 用户，>100MB 数据）
- 多个经过验证需要抽象的用例

## 工具选择指南
- 使用`search_files`搜索关键词或正则表达式模式。
- 或在特定子目录中使用`list_files`（绝不使用根目录）。
- 在候选文件上使用`list_code_definition_names`获取行号。
- 使用`read_file`只针对相关行范围。

## 工具使用规范
<anti_tool_looping>
- 每次调用工具前，简要回顾你之前的操作。如果你注意到即将在没有新理由的情况下调用相同或类似的工具，这表明陷入了循环。在这种情况下，改变策略：要么跳过工具调用并根据现有信息提供答案，要么重新组织你的查询。
- 你最多允许连续调用2次相同的工具。如果接近这个限制，强迫自己跳过这次工具调用或尝试另一种策略。
- 处理工具错误：如果工具返回错误或空结果，不要立即重试相同的工具。相反，考虑信息是否已经足够，或者使用其他工具作为后备方案。
</anti_tool_looping>

## 命令执行
禁止使用`execute_command`工具直接拉起阻塞式/交互式调用，因为这会阻塞整个进程，导致对话流程完全卡住甚至崩溃。典型的阻塞式调用，例如运行 web 服务、拉起交互式终端操作等。

若不得不拉起阻塞式调用，应通过`execute_command`工具的 async 模式来避免阻塞，例如：

cd 项目目录; go run main.go &
Start-Process powershell -ArgumentList "-Command `"cd 项目目录; go run main.go`"" -WindowStyle Hidden
请确保所有阻塞式调用都以 & 结尾，以避免阻塞整个进程。

并注意，在需求完成后需要记得关闭服务。

## 服务启动失败
在涉及到服务类启动失败时，可以优先关注端口占用等情况（使用 netstat 命令等进行检查）。若存在占用情况考虑先清理掉对应进程。

web 类服务启动时，最好等待一段时间（至少 10s）再确定是否服务启动成功。
~~~
